> - 앞선 글: [케라스 API로 구현한 합성곱 신경망](../keras-api-1/)

앞선 글에서 5-3절의 CIFAR-10 분류기(합성곱 신경망)를 케라스로 옮겼다. 그때 파이토치 API와 케라스 API로 구현한 두 모델의 파라미터 수는 532,970개로 **정확히 같았다.** 같은 모델을 다른 API로 만든 것이라는 증거였다.

이 글에서는 6-3절의 띄어쓰기 모델(순환 신경망)을 케라스 API로 바꿔 본다. 그런데 이번에는 파라미터 수가 **달라진다.**

| 모델                                | 파이토치 | 케라스  | 차이  |
| ----------------------------------- | -------- | ------- | ----- |
| 단순 RNN (`hidden_size=256`, 2계층) | 213,762  | 213,250 | 512   |
| LSTM (같은 설정)                    | 853,506  | 851,458 | 2,048 |

구현 실수 때문이 아니다. 파이토치 API와 케라스 API가 **순환 신경망 모델을 다른 방식으로 구현**하기 때문이다. 이번 문서에서는 차이가 발생하는 이유, 그리고 그것이 의미하는 바를 설명하는 데 집중한다. 구현하는 API를 옮겨 다닐 때 마주치는 전형적인 함정이라, 케라스 API를 사용할 계획이 없더라도 알아둘 가치가 있다.

> 앞선 글에서 설명한 내용은 다시 다루지 않는다. [keras-api-1](../keras-api-1/)을 이미 읽었다고 가정하므로, 필요하다면 읽어 두자.

## 1. 순차 데이터를 다룰 때 달라지는 점

좋은 소식부터 전하자면, **데이터 쪽은 손댈 것이 없다.**

합성곱 신경망의 케라스 API 구현에서는 이미지 텐서의 채널 위치를 `channels_first`로 파이토치 이미지 텐서와 같은 형태로 맞춰야 했다. 하지만 순차 데이터에는 그런 문제가 없다. 두 API 모두 `(B, S, input_size)`라는 형태의 텐서를 사용한다.

> 물론 본문에서 설명했듯, 파이토치의 기본 설정은 `(S, B, ...)`이며, `batch_first=True`를 지정해 `(B, S, ...)`로 바꿔야 배치 차원이 가장 앞에 위치하는 직관적인 구조가 된다. 

그래서 6-3절의 `making_spacing_example()`, `SpacingDataset`, 어휘 사전, `DataLoader`는 **한 글자도 고치지 않고** 그대로 쓸 수 있다. 이 글의 예제 노트북은 이 부분에서 본문 [코드 6-9]~[코드 6-10]과 6-3절 예제 노트북의 `making_spacing_example()`을 그대로 가져다 쓰고 있다.

## 2. 모델 정의 - 무엇이 바뀔까?

본문 [코드 6-11]의 `SpacingRNN`과 케라스 API 구현을 나란히 놓고 비교해 보자.

```python
# 본문 [코드 6-11]
class SpacingRNN(nn.Module):
    def __init__(self, input_size, hidden_size, num_layers, output_size):
        super().__init__()
        self.rnn = nn.RNN(input_size=input_size, hidden_size=hidden_size,
                          num_layers=num_layers, batch_first=True)
        self.fc = nn.Linear(hidden_size, output_size)

    def forward(self, x):                   # (B, S, input_size)
        outputs, _ = self.rnn(x)            # -> (B, S, hidden_size)
        last_hidden = outputs[:, -1, :]     # -> (B, hidden_size)
        return self.fc(last_hidden)         # -> (B, output_size)
```

```python
# 케라스 API
model = keras.Sequential([
    layers.Input(shape=(SEQUENCE_LENGTH, vocab_size)),
    layers.SimpleRNN(HIDDEN_SIZE, return_sequences=True),
    layers.SimpleRNN(HIDDEN_SIZE),
    layers.Dense(OUTPUT_SIZE),
])
```

### `batch_first=True`가 사라진다

파이토치의 `nn.RNN`은 **기본값이 `(S, B, input_size)`로** 시간 축이 먼저 온다. 순환 신경망의 계산은 시점 단위로 진행되므로 그 축이 앞에 있는 편이 구현에 편리하기 때문인데, 다른 계층과 형태가 달라 헷갈리기 쉽다. 그래서 본문은 `batch_first=True`를 주어 `(B, S, input_size)`로 맞췄다. 

케라스 API에서는 **언제나 배치가 먼저**이므로, 이런 설정이 필요하지 않다. 

### `num_layers`가 사라지고 계층이 두 개가 된다

파이토치의 `nn.RNN`은 `num_layers` 인자 하나로 순환 계층을 수직으로 쌓는다. 계층 두 개가 `self.rnn` 하나 안에 들어 있고, 파라미터 이름의 `_l0`, `_l1` 접미사로만 구분된다.

케라스의 **순환 계층 객체 하나는 한 층만 표현**하며, 두 층을 쌓으려면 객체 두 개를 만들어 사용해야 한다. 코드는 길어지지만 나쁜 것만은 아니다. 계층마다 `hidden_size`를 다르게 주거나, 사이에 드롭아웃이나 정규화 계층을 끼워 넣기가 쉬워진다. 물론 파이토치에서도 설정이 다른 `nn.RNN`을 여러 개 생성하고 직접 이어서 같은 일을 할 수 있다.

### `outputs[:, -1, :]`가 `return_sequences`로 바뀐다

가장 중요한 지점이다. 

파이토치의 `nn.RNN`은 **모든 시점의 출력을 돌려준다.** 본문의 예제에서 `outputs[:, -1, :]`로 마지막 시점만 잘라 낸 것처럼 무엇을 쓸지를 사용자가 정해야 한다. 띄어쓰기 모델은 윈도우 마지막 글자 뒤에 공백이 오는지만 판단하면 되므로 마지막 시점이면 충분하다.

케라스 API에서는 **계층을 만들 때 미리** 선택을 한다.

|                                   | 출력 형태             | 쓰는 곳                     |
| --------------------------------- | --------------------- | --------------------------- |
| `return_sequences=True`           | `(B, S, hidden_size)` | 뒤에 순환 계층을 더 쌓을 때 |
| `return_sequences=False` (기본값) | `(B, hidden_size)`    | 마지막 시점만 필요할 때     |

계층을 쌓을 때는 **마지막을 제외한 모든 순환 계층을 `True`로** 지정해야 한다. 다음 순환 계층에 모든 시점의 상태를 전달해야 하기 때문이다. 마지막 계층을 기본값 `False`로 두면 본문 예제의 `outputs[:, -1, :]`와 같이 마지막 시점의 상태만 출력한다.

케라스 구현에서는 `return_sequences=True`를 빠뜨리는 실수를 범하기 쉽다. 다행인 것은 이런 종류의 실수는 형태 오류로 인한 예외가 발생한다는 점이다.

정리하면, 파이토치는 **출력을 다 주고 나중에 골라야** 하고, 케라스는 **미리 정한 것만 반환한다.**

## 3. 파라미터 수가 왜 다른가

가장 중요한 차이는 모델 파라미터의 구성이 달라진다는 점이다. 파이토치 API로 구현한 모델과 케라스 API로 구현한 모델의 파라미터를 하나씩 대조해 보면 다음과 같다.

| 파이토치           | 형태         |     | 케라스             | 형태         |
| ------------------ | ------------ | --- | ------------------ | ------------ |
| `rnn.weight_ih_l0` | `(256, 61)`  | ↔   | `kernel`           | `(61, 256)`  |
| `rnn.weight_hh_l0` | `(256, 256)` | ↔   | `recurrent_kernel` | `(256, 256)` |
| `rnn.bias_ih_l0`   | `(256,)`     | ↘   | `bias`             | `(256,)`     |
| `rnn.bias_hh_l0`   | `(256,)`     | ↗   |                    |              |

### 가중치 행렬은 전치되어 있을 뿐이다

파이토치의 `weight_ih_l0`은 `(256, 61)`이고 케라스의 `kernel`은 `(61, 256)`이다. 행과 열이 뒤바뀌었지만 원소 수는 15,616개로 같다.

계산의 표기 방향이 다를 뿐이다. 파이토치의 `nn.Linear`는 `y = xWᵀ + b`로 계산하므로 가중치를 `(출력, 입력)` 순서로 저장하고, 케라스는 `y = xW + b`로 계산하므로 `(입력, 출력)` 순서로 저장한다. 

### 편향 텐서의 개수가 다르다

파이토치는 순환 계층마다 편향을 **두 개** 갖는다. `bias_ih_l0`과 `bias_hh_l0`이다.

[그림 6-3]의 단순 RNN 구조를 수식으로 쓰고 이를 구현한다고 생각해 보자. 파이토치 API로 구현하면 다음과 같다.

```text
h_t = tanh(W_ih · x_t + b_ih  +  W_hh · h_{t-1} + b_hh)
```

그런데 케라스 API는 다음과 같이 달라진다.

```text
h_t = tanh(W_ih · x_t  +  W_hh · h_{t-1}  +  b)
```

**두 식은 본질적으로는 동일하다.** `b_ih + b_hh`는 상수 벡터 두 개의 합이고, 그 합은 언제나 하나의 벡터 `b`로 나타낼 수 있다. 파이토치 API로 표현할 수 있는 함수의 집합과 케라스 API로 표현할 수 있는 함수의 집합은 완전히 같다. 

그런데도 파이토치 API가 두 개의 편향 텐서를 사용하는 이유는 엔비디아의 cuDNN 라이브러리 때문이다. GPU에서 순환 신경망을 빠르게 돌리는 커널이 편향을 둘로 나눠 받도록 설계되어 있어서, 파이토치는 그 관례를 그대로 파라미터로 노출한다. 성능을 위해 수학적 간결함을 내준 셈이다.

차이는 `hidden_size × num_layers × 부품 개수`와 정확히 들어맞는다.

| 모델     | 부품(가중치 블록) 개수 | 계산        | 차이  |
| -------- | --------- | ----------- | ----- |
| 단순 RNN | 1         | 256 × 2 × 1 | 512   |
| GRU      | 3         | 256 × 2 × 3 | 1,536 |
| LSTM     | 4         | 256 × 2 × 4 | 2,048 |

> GRU의 경우 `reset_after=False`로 설정한 경우이다.

### 그래서 무엇이 달라지나

**학습에는 사실상 영향이 없다.** 늘어난 편향 파라미터가 모델의 표현력을 넓히지 않기 때문이다. 두 구현은 같은 함수의 집합 위에서 최적화한다. 파이토치 API와 케라스 API로 구현한 두 모델의 학습 곡선을 그려 보면 비슷한 경향을 보인다.

하지만 알아 두어야 할 것이 둘 있다.

1. **파라미터 수를 그대로 비교하면 안 된다.** 논문이나 코드에 적힌 순환 신경망의 파라미터 수가 구현마다 조금씩 다르다면, 구현이 틀린 것이 아니라 프레임워크가 다른 것일 수 있다.
2. **가중치를 옮길 때는 변환이 필요하다.** 파이토치에서 학습한 파라미터를 케라스 모델에 넣으려면 가중치는 전치하고, 두 편향은 더해서 하나로 만들어야 한다. (연습 문제 7번)

5-3절의 합성곱 신경망에서는 없었던 상황이다. `nn.Conv2d`와 `layers.Conv2D`는 둘 다 필터당 편향 하나만 두기 때문이다. **순환 신경망에서만 생기는 차이다.**

## 4. 기울기 클리핑 - 학습 루프 밖으로

본문 [코드 6-12]는 학습 함수 안에서 역전파 직후, 최적화 직전에 기울기 클리핑을 걸었다.

```python
loss.backward()
torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
optimizer.step()
```

케라스 API에서는 `fit()`이 학습 루프를 대체하므로 기울기 클리핑을 학습 루프에 추가할 수 없다. 대신 **옵티마이저를 만들 때 인자로** 지정한다.

```python
keras.optimizers.Adam(learning_rate=LR, global_clipnorm=1.0)
```

`global_clipnorm`이 본문의 `max_norm`에 해당한다. 전체 파라미터의 기울기를 하나의 벡터로 보고 그 노름이 1.0을 넘으면 1.0으로 줄인다. 기울기의 크기만 줄고 방향은 그대로이므로 본문의 `clip_grad_norm_()`과 계산 결과가 같다.

그런데 비슷한 이름의 **`clipnorm`과 `clipvalue`는 다른 것이다.** `clipnorm`은 가중치 텐서마다 따로 노름을 재고 클리핑을 하며(그 결과 전체 기울기의 방향이 달라질 수 있다), `clipvalue`는 노름이 아니라 원소마다 값을 기준으로 클리핑을 해 기울기의 **방향이 바뀐다.** 6-3절이 설명한 기울기 클리핑은 `global_clipnorm`에 대응한다. 참고로 `clipvalue`는 파이토치 함수 `clip_grad_value_()`에 대응한다.

이 부분은 `fit()`의 성격을 잘 보여 준다. 학습 루프의 중간에 끼어드는 일은 **미리 정해진 방식으로만** 가능하고, 미리 정해진 방식이 없다면 할 수 없다. 기울기 클리핑의 경우 옵티마이저 인자로 지정할 수 있어 쉽게 옮길 수 있지만, 이런 통로가 마련되어 있지 않은 기능은 `fit()`을 포기하고 학습 단계를 직접 구현해야 한다. 또한 통로가 있더라도 이름만 보고 골라서는 안 된다. `clipnorm`처럼 이름이 비슷해도 세부 동작이 다를 수 있으므로 문서에서 정확한 동작을 확인해야 한다.

## 5. 예측 - 모든 윈도우를 한 번에 입력해 예측

본문 [코드 6-13]의 `make_spacing()`은 배치 크기 1인 데이터로더를 만들어 윈도우를 하나씩 모델에 넣고 결과를 문자열에 이어 붙였다.

```python
for input_sample, _ in dataloader:
    input_sample = input_sample.to(device)
    prediction = model(input_sample)
    is_spacing = torch.argmax(prediction, dim=1).item()
    spacing_sequence += str(is_spacing)
```

케라스의 `predict()`는 데이터로더를 통째로 받아 **배치에 포함된 모든 윈도우의 예측을 한 번에** 수행한다.

```python
predictions = model.predict(dataloader, verbose=0)   # (윈도우 수, 2)
spacing_sequence = ''.join(str(i) for i in predictions.argmax(axis=1))
```

루프도, `.to(device)`도, `model.eval()`도, `torch.no_grad()`도 없다. 예측 결과를 문자열로 되돌리는 뒷부분은 본문과 똑같다. 모델 바깥의 코드이기 때문이다.

덧붙여, 케라스 API 예제의 예측 속도는 배치 크기가 1인 본문 예제의 예측 속도보다 빠른데, 이는 케라스 API가 빠른 것이 아니라 **배치로 묶어 예측하는 편이 빠르기 때문**이다.

### 예측 결과는 본문 예제와 맥락이 같다

예제 노트북은 본문과 같은 두 문장으로 예측을 시험한다. 결과를 모아 보면 이렇다.

| 테스트 입력        | 단순 RNN  | LSTM      |
| ------------------ | --------- | --------- |
| 학습 텍스트의 일부 | 90.4%     | **99.2%** |
| 학습에 없는 문장   | **95.9%** | 92.8%     |

학습 텍스트 안에서는 LSTM이 뚜렷하게 앞선다. 본문이 말한 장기 의존성의 효과다. 반면 처음 보는 문장에서는 격차가 사라지고 오히려 단순 RNN이 조금 낫다. LSTM의 훈련 정확도가 99%를 넘긴 것을 보면 이미 과적합이 진행된 상태일지도 모른다. 본문 [그림 6-14]가 검증 F1 점수로 보여 준 것과 같은 현상일 수 있고, 6-3절이 조기 종료를 이야기한 이유이기도 하다.

숫자는 실행할 때마다 달라지지만 이 방향은 본문의 설명과 어긋나지 않는다.

---

## 6. 얻은 것과 잃은 것

6-3절의 예제를 케라스 API로 옮기면서 생략된 부분을 확인해 보자.

- 학습 함수 `train_epoch()` - 전부
- 에포크 반복 루프와 `EpochLogger` - 전부
- `model.to(device)`, `inputs.to(device)`, `labels.to(device)` - 전부
- `model.train()`, `model.eval()`, `torch.no_grad()` - 전부
- 예측 루프 - 두 줄로

대신 코드에서 감춰진 것들이 있다.

- **기울기가 언제 초기화되는지** 보이지 않는다. 본문의 `optimizer.zero_grad()`가 사라졌다.
- **손실이 어떻게 집계되는지** 보이지 않는다. 본문은 배치마다 샘플 수로 가중해 더했다. 케라스도 같은 일을 하지만 코드에 없다.
- **기울기 클리핑이 역전파와 최적화 사이에** 들어간다는 사실이 보이지 않는다. `global_clipnorm=1.0`이라는 인자만 남는다.

이 셋은 모두 본문에서 따로 설명한 것들이다. 처음부터 케라스 API로 `fit()`만 사용해 보면 이런 것들을 이해하기 어렵다.

## 7. 속도 - 추상화의 허점

예제 노트북을 돌려 보면 예상 밖의 일이 벌어진다. **LSTM이 단순 RNN보다 빠르다.** LSTM은 부품이 네 개라 계산량이 몇 배 많은데도 그렇다.

같은 하드웨어(RTX 4070 SUPER)에서 에포크당 시간을 재면 이렇다.

| 1 에포크 | 파이토치 | 케라스 | 비율      |
| -------- | -------- | ------ | --------- |
| 단순 RNN | 9.9초    | 87.6초 | **8.9배** |
| LSTM     | 13.0초   | 34.4초 | 2.6배     |

이유는 cuDNN에 있다. 3절에서 파이토치가 편향을 두 개 두는 이유로 언급했던 그 라이브러리다. cuDNN은 순환 신경망의 시점 반복을 GPU 커널 하나로 융합해 처리해 준다. 파이토치는 `nn.RNN`과 `nn.LSTM` 모두 이 경로를 타지만, 케라스의 파이토치 백엔드는 `LSTM`과 `GRU`만 이 경로로 내려보내고 **`SimpleRNN`에는 그런 경로가 없다.** `SimpleRNN`은 시점 25개를 파이썬 수준에서 하나씩 반복한다.

케라스 API가 느리다는 이야기는 아니다. 앞선 글에서 본 합성곱 신경망의 1.3배와 이번 글의 단순 RNN의 8.9배는 성격이 다른 숫자다. 앞의 것은 배치마다 붙는 고정 비용이지만, 뒤의 것은 **빠른 길이 없다는 신호**다.

추상화된 고수준 API는 잘 닦인 길에서는 사용성과 성능 양 측면에서 쾌적하게 달려 나갈 수 있지만, 그 길을 벗어나면 성능이 급격히 떨어질 수 있고, 아예 길이 없는 경우 사용성도 떨어진다. 가려는 길이 어떤지는 문서를 찾아보거나 직접 구현한 후 확인해 봐야 알 수 있다. 

> 파이토치라고 다르지 않다. CPU에서 실행하거나 `nn.LSTMCell` 등으로 시점 루프를 직접 작성하면 cuDNN 융합 커널을 쓰지 않는다. 다만 파이토치는 `nn.RNN`, `nn.LSTM`, `nn.GRU`가 모두 같은 cuDNN 경로를 쓰므로 계층 종류에 따른 편차가 적다.

### 예제 노트북을 돌릴 때

이 때문에 예제 노트북 전체를 실행하는 데 꽤 오랜 시간이 소요된다(저자의 경우 단순 RNN 20에포크 약 29분, LSTM 20에포크 약 12분). 본문 예제와 일관성을 맞추기 위해 에포크 수를 20으로 두었기 때문인데, `EPOCHS`를 5 정도로 줄여도 두 모델의 학습 곡선을 비교하거나 경향을 확인하기에 충분하다.

## 8. 그 다음 - 케라스로는 어려운 것들

6장의 예제까지는 케라스 API로 구현하기가 어렵지 않다. 하지만 이후의 예제는 사정이 달라진다.

- **가변 길이 시퀀스**(9장). 파이토치의 `pack_padded_sequence`에 해당하는 것이 없다. 케라스는 `Masking` 계층이나 `mask_zero=True`로 비슷한 일을 하지만 방식이 다르다.
- **Seq2Seq와 어텐션**(9장). `MultiHeadAttention`은 있지만, 디코더의 시점별 루프를 직접 제어하려면 결국 학습 단계를 직접 써야 한다.
- **트랜스포머**(10장). `nn.TransformerEncoderLayer`에 해당하는 것이 케라스 본체에 없다. 별도 패키지인 KerasHub가 필요하다.

## 연습 문제

**1.** 예제 노트북의 `build_spacing_model()`에서 마지막 순환 계층에도 `return_sequences=True`를 주면 어떤 오류가 나는지 확인한 후, 이 오류에 대해서 설명해 보자.

**2.** `NUM_LAYERS`를 3으로 바꿔 두 프레임워크의 파라미터 수를 다시 세어 보자. 차이가 `hidden_size × num_layers` 공식대로 늘어나는지 확인해 보자.

**3.** 본문 6-3절은 `nn.GRU`도 같은 방식으로 교체할 수 있다고 했다. `layers.GRU`로 세 번째 모델을 만들어 학습시키고 학습 곡선을 비교해 보자. 그리고 GRU의 부품 수(3개)에 맞춰 파라미터 수의 차이를 먼저 예측한 다음 확인해 보자.

> 힌트: 예측이 빗나갔다면 `reset_after` 설정을 확인해 보자.

**4.** 4절의 `global_clipnorm=1.0`을 `clipnorm=1.0`과 `clipvalue=1.0`으로 차례로 바꿔 가며 학습해 보자. 학습 곡선이 어떻게 달라지는지 관찰하고, 6-3절이 설명한 기울기 클리핑이 왜 `global_clipnorm`에 대응하는지 설명해 보자.

**5.** 5절의 `make_spacing()`은 `predict()`에 배치 크기 `BATCH_SIZE`인 데이터로더를 넘긴다. 본문처럼 배치 크기를 1로 바꾸면 예측 시간이 얼마나 달라지는지 재 보자.

**6.** [도전 문제] 본문 예제 노트북은 원본 순차 데이터를 8:2로 먼저 나눈 뒤 데이터셋을 만들어 과적합을 관찰했다. 같은 방식으로 검증 데이터셋을 만들어 `fit(validation_data=...)`에 넘기고, `EarlyStopping` 콜백으로 조기 종료를 적용해 보자.

> 힌트: 띄어쓰기는 불균형 분류이므로 정확도보다 F1 점수가 낫다. `keras.metrics.F1Score`를 `compile(metrics=...)`에 넣을 수 있다.

**7.** [도전 문제] 파이토치 `SpacingRNN`의 학습된 파라미터를 케라스 모델로 **옮겨** 보자. 가중치는 전치하고, 두 편향은 더해서 하나로 만들면 된다. 옮긴 뒤 두 모델이 같은 입력에 같은 출력을 내는지 확인해 보자. 3절의 "두 식은 본질적으로는 동일하다"는 주장을 직접 검증하는 문제다.

> 힌트: `keras_layer.set_weights([kernel, recurrent_kernel, bias])` 순서다.

연습 문제의 풀이는 따로 싣지 않았다. 모두 예제 노트북의 코드를 조금씩 고쳐 직접 돌려 보는 문제이고, **결과를 예상한 다음 확인하는 것**이 이 문제들의 요점이기 때문이다. 다시 학습시켜야 하는 문제는 시간이 걸리므로 에포크 수를 줄여 경향만 확인해도 된다.
