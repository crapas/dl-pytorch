이 책은 내부 구현과 API 모두 파이토치를 기준으로 한다.

하지만 파이토치 API를 통해서만 파이토치를 사용할 수 있는 것은 아니다. **케라스**(Keras) API를 사용해서도 구현할 수 있다. 케라스 API는 파이토치 API와 모습과 사용법이 꽤 다르지만, 파이토치 프레임워크 위에서 동작하는 파이토치 모델을 만들 수 있다. 한 걸음 더 나아가 케라스 API는 텐서플로와 JAX 프레임워크와도 호환되므로 케라스 API는 익혀 둘 만한 가치가 있다.

이 문서는 본격적인 케라스 API 학습을 목표로 하지 않는다. 우선은 케라스 API로 구현된 코드를 읽고 이해하는 정도의 지식을 목표로 한다. 이를 위해 5-3절의 CIFAR-10 분류기를 케라스로 구현하는 과정을 파이토치 API의 구현 방식과 비교하며 설명한다.

> 케라스 API는 모든 파이토치 API를 대체할 수 없다. 케라스가 보장하는 것은 여러 백엔드에서 공통으로 지원되는 연산만 추상화해 대표적인 고수준 API를 대체하는 수준이다. 그래서 데이터셋과 데이터로더 같은 파이토치의 고유 기능은 직접 파이토치 API를 호출해야 한다.

## 1. 케라스는 무엇인가

케라스는 2015년에 나온 딥러닝 라이브러리로, 당시 백엔드는 테아노(Theano)였다. 그 뒤 텐서플로가 공개되면서 텐서플로 백엔드가 추가되었고, 이후 오랫동안 텐서플로의 고수준 API로도 사용되어 왔다. 특히 텐서플로가 케라스를 자체 API로 흡수하면서 한때 텐서플로의 전용 API로 활용되기도 했다.

하지만 2023년에 나온 **케라스 3**부터는 성격이 달라졌다. 텐서플로에 매이지 않고 파이토치와 JAX도 지원하는 멀티 백엔드 API로 변신했다(JAX는 Google이 개발한 수치 연산, 자동 미분 라이브러리로 딥러닝 전문 라이브러리라기보다는 미분 기능이 포함된 병렬 처리 넘파이 라이브러리에 가깝다).

케라스 백엔드로 파이토치를 선택하면 다음과 같이 동작하는 모델을 만들 수 있다.

- 실제 연산은 파이토치 프레임워크가 담당한다. 텐서도 `torch.Tensor` 객체로 생성되고, 하드웨어 가속기도 파이토치의 라이브러리를 통해 활용한다.
- `Dataset`과 `DataLoader`를 포함한 파이토치의 데이터 파이프라인을 그대로 사용할 수 있다.
- 파이토치 생태계의 다른 도구(`torchvision` 등)도 함께 쓸 수 있다.

즉 케라스 3 + 파이토치 백엔드는 파이토치의 대체제가 아니라, 케라스에 익숙한 사람을 위한 파이토치, 또는 텐서플로에서도 동작하는 딥러닝 모델 코드를 만들기 위한 선택이다.

### 설치

```bash
pip install keras
```

파이토치가 이미 설치되어 있다면 이것만으로 설치가 끝난다.

### 백엔드 지정

백엔드는 `keras`를 **임포트하기 전에** 환경 변수로 정한다.

```python
import os
os.environ['KERAS_BACKEND'] = 'torch'   # 반드시 import keras 앞에

import keras
print(keras.backend.backend())          # torch
```

임포트한 뒤에 환경 변수를 바꿔도 반영되지 않는다. 케라스가 임포트 시점에 백엔드를 확정하기 때문이다. 노트북에서 케라스 임포트를 먼저 해버렸다면 커널을 다시 시작해야 한다.

환경 변수 대신 홈 디렉터리의 `~/.keras/keras.json` 파일에 적어 둘 수도 있다. 다만 예제 노트북처럼 다른 환경에서도 그대로 돌아가야 하는 코드라면 환경 변수 쪽이 안전하다.

### 이미지 텐서의 형태(채널의 위치)

파이토치의 이미지 텐서는 채널을 앞에 둔 `(B, C, H, W)` 형태이지만, 텐서플로를 거쳐 온 케라스에서는 텐서플로에서 사용한 `(B, H, W, C)`, 즉 채널이 뒤에 위치한 형태의 이미지 텐서를 기본값으로 한다. 하지만 굳이 텐서 차원의 순서를 바꾸지 않고 다음과 같은 설정 코드 한 줄로 파이토치의 이미지 텐서를 그대로 사용할 수 있고, 본문 예제의 데이터로더도 수정 없이 그대로 사용 가능하다.

```python
keras.config.set_image_data_format('channels_first')
```

이 설정을 빠뜨리면 합성곱 계층이 32를 채널 수로 착각해 엉뚱한 형태 오류를 만나게 된다.

## 2. 무엇이 어떻게 바뀌나?

5-3절의 예제에서 사용한 파이토치 API 요소에 대응하는 케라스 API 요소를 정리하면 다음과 같다.

| 파이토치 API                                                 | 케라스 API                                                      |
| ------------------------------------------------------------ | --------------------------------------------------------------- |
| `nn.Module` 상속 클래스                                      | `keras.Sequential` 또는 `keras.Model` 상속 클래스               |
| `nn.Conv2d(3, 16, 5, 1, 2)`                                  | `layers.Conv2D(16, 5, padding='same')`                          |
| `nn.ReLU()`, `nn.MaxPool2d(2)`                               | `layers.ReLU()`, `layers.MaxPooling2D(2)`                       |
| `nn.Flatten()`, `nn.Linear(2048, 256)`                       | `layers.Flatten()`, `layers.Dense(256)`                         |
| `nn.Dropout(p=0.5)`                                          | `layers.Dropout(0.5)`                                           |
| `print(model)`                                               | `model.summary()`                                               |
| `nn.CrossEntropyLoss()`                                      | `compile(loss=SparseCategoricalCrossentropy(from_logits=True))` |
| `optim.Adam(model.parameters(), lr=LR)`                      | `compile(optimizer=Adam(learning_rate=LR))`                     |
| `train_batch()`, `valid_batch()`, `train_with_early_stopping()` | `fit()`                                                         |
| 조기 종료 판단과 `best_model_params`                         | `EarlyStopping` 콜백                                            |
| `common.EpochLogger`                                         | `fit()`의 진행 표시와 반환값 `History`                          |
| `common.get_accuracy()`                                      | `model.evaluate()`                                              |
| `torch.device()`와 `.to(device)`                             | (없음 - 케라스가 처리)                                          |
| `model.train()` / `model.eval()`                             | (없음 - `fit()`과 `evaluate()`가 전환)                          |
| `Dataset`, `DataLoader`                                      | **그대로 사용**                                                 |
| `transforms.Compose`                                         | **그대로 사용** (증강은 예외, 5절 참고)                         |

오른쪽 열에서 '없음'과 '그대로 사용'에서 알 수 있듯, **데이터를 다루는 방법은 바뀌지 않고, 모델을 정의하고 학습시키는 방법만 바뀐다.**

## 3. 모델 정의 - 입력 채널을 세지 않는다

본문 [코드 5-13]의 `CIFAR10ConvClassifier`를 케라스로 옮기면 이렇게 된다.

```python
from keras import layers

model = keras.Sequential([
    layers.Input(shape=(3, 32, 32)),
    layers.Conv2D(16, 5, padding='same'), layers.ReLU(), layers.MaxPooling2D(2),
    layers.Conv2D(32, 3, padding='same'), layers.ReLU(), layers.MaxPooling2D(2),
    layers.Flatten(),
    layers.Dense(256), layers.ReLU(),
    layers.Dense(10),
])
```

본문과 다른 점이 두 가지 있다.

**입력 채널 수를 쓰지 않는다.** 파이토치 API는 `nn.Conv2d(in_channels=3, out_channels=16, ...)`처럼 입력과 출력을 모두 적었고, 두 번째 블록의 `in_channels=16`은 앞 블록의 출력을 보고 직접 맞춰야 했다. `nn.Linear(32 * 8 * 8, 256)`의 2048도 두 번의 풀링을 거친 크기를 손으로 계산한 값이다. 케라스는 `Input`에 준 형태에서 시작해 각 계층의 입력 크기를 스스로 계산해 적용한다. 계층을 하나 추가해도 이어지는 계층의 채널 수를 고칠 필요가 없다.

**패딩을 숫자가 아니라 이름으로 준다.** 본문의 `padding=2`(5x5 필터)와 `padding=1`(3x3 필터)은 모두 "출력 크기를 입력과 같게 유지"하려는 것이었다. 5-2절의 출력 크기 공식에 스트라이드 1을 넣어 보면, 필터 크기가 홀수 `k`일 때 출력 크기를 유지하는 패딩은 `(k-1)/2`다. 케라스는 이 의도를 `padding='same'`이라는 이름으로 받는다. 패딩을 아예 주지 않으려면 `padding='valid'`로 지정하면 된다.

두 모델의 파라미터 수는 **532,970개로 정확히 같다.** 계층별 출력 형태도 같다. 같은 모델을 다른 표기법으로 적은 셈이다.

### 같은 구조라고 결과까지 같지는 않다

파라미터 수가 같아도 학습 결과의 숫자는 일치하지 않는다. 가중치의 **초깃값을 정하는 방식**이 다르기 때문이다.

|                        | 가중치           | 편향                  |
| ---------------------- | ---------------- | --------------------- |
| 파이토치 `nn.Conv2d`   | 카이밍 균등 분포 | fan_in 기반 균등 분포 |
| 케라스 `layers.Conv2D` | 글로럿 균등 분포 | **0**                 |

초깃값이 다르면 경사 하강이 지나는 경로가 달라지고, 도착점도 달라진다. 그러니 두 구현을 비교할 때 볼 것은 소수점 아래 숫자가 아니라 **경향**이다.

예제 노트북의 결과를 본문 [표 5-6]과 나란히 놓아 보자.

| 구분            | 최적 에포크 (본문 / 케라스) | 평가 정확도 (본문 / 케라스) |
| --------------- | --------------------------- | --------------------------- |
| 기본 모델       | 7 / 7                       | 69.33% / 67.62%             |
| 증강 적용       | 11 / 8                      | 72.26% / 72.74%             |
| 증강 + 드롭아웃 | 17 / 18                     | 72.68% / 74.09%             |

숫자는 조금씩 어긋나지만 **결과가 알려주는 내용은 크게 바뀌지 않는다.** 증강을 넣으면 과적합이 늦춰져 최적 에포크가 뒤로 밀리고, 드롭아웃을 더하면 더 밀린다. 평가 정확도는 두 처방을 더할 때마다 올라간다. 다만 본문에서는 드롭아웃을 더하면 훈련 정확도가 낮아지면서 훈련–평가 정확도 차이가 줄었지만, 이번 실행에서는 그 차이가 8.39%p에서 10.79%p로 오히려 커졌다. 초깃값과 실행 환경에 따라 달라질 수 있는 부분이다.

## 4. 학습 - 단 두 개의 함수 호출로 끝

두 구현에서 가장 큰 차이가 나는 부분이다.

파이토치 API를 사용하면 학습 루프를 직접 구현해야 한다. 에포크를 반복하고, 미니배치를 구성하고, 기울기를 초기화하고, 순전파와 역전파를 거치면서 손실을 샘플 수로 가중해 누적하고, 검증 손실의 최솟값을 추적해 조기 종료를 판단하고, 최적 파라미터를 복사해 두었다가 되돌렸다. `train_batch()`, `valid_batch()`, `train_with_early_stopping()` 세 함수에 걸쳐 60줄 남짓의 코드가 필요했다.

케라스에서는 다음과 같이 바뀐다.

```python
model.compile(
    optimizer=keras.optimizers.Adam(learning_rate=LR),
    loss=keras.losses.SparseCategoricalCrossentropy(from_logits=True),
    metrics=['accuracy'],
)

history = model.fit(
    train_loader,                       # 파이토치 DataLoader 를 그대로 사용
    validation_data=valid_loader,
    epochs=EPOCHS,
    callbacks=[keras.callbacks.EarlyStopping(
        monitor='val_loss', patience=PATIENCE, restore_best_weights=True)],
)
```

`compile()`은 **무엇으로 학습할지**(손실 함수, 옵티마이저, 지켜볼 지표)를 정하고, `fit()`은 **학습을 실행한다.** 두 단계로 나뉘어 있는 것이 처음에는 어색하지만, 본문 예제에서 `criterion`과 `optimizer`를 먼저 만들고 그다음에 학습 루프를 실행한 것과 같은 순서와 구성이다.

### 긴 이름의 손실 함수

`SparseCategoricalCrossentropy(from_logits=True)`는 본문의 `nn.CrossEntropyLoss()`와 **같은 교차 엔트로피 손실 함수다.** 긴 이름에는 파이토치가 기본값으로 정해 둔 두 가지를 겉으로 드러내고 있다.

- **`Sparse`** - 정답을 원-핫 벡터가 아니라 클래스의 고유 번호를 사용한다는 뜻이다. 원-핫 벡터를 정답으로 사용하는 경우 `Sparse`를 뺀 `CategoricalCrossentropy`를 손실 함수로 사용한다.
- **`from_logits=True`** - 모델의 출력이 확률이 아니라 로짓이라는 뜻이다. 3-3절에서 본 대로 본문의 모델도 마지막에 소프트맥스 없이 로짓을 그대로 반환한다.

`from_logits`를 빠뜨리는 것이 케라스에서 가장 흔한 실수다.
기본값이 `False`라서, 모델이 로짓을 내보내는데도 케라스는 그것을 확률로 믿고 손실을 계산한다. 이 경우 오류 발생 없이 **조용히 잘못된 손실로 학습된다.** 정확도가 이유 없이 낮다면 이 부분을 먼저 살펴보자.

### 콜백

`fit()`이 학습 루프를 가져간 대신, 루프 중간에 끼어들 자리를 **콜백**(callback)으로 열어 둔다. 본문의 조기 종료 코드는 `EarlyStopping()` 콜백 함수를 통해 적용된다.

| 본문 예제                       | 대응하는 `EarlyStopping()` 함수의 인자 |
| ------------------------------- | -------------------------------------- |
| `best_valid_loss` 추적          | `monitor='val_loss'`                   |
| `patience_counter`              | `patience=PATIENCE`                    |
| `best_model_params` 복사와 복원 | `restore_best_weights=True`            |

`restore_best_weights`의 기본값은 `False`다. 이때는 학습이 멈춘 마지막 에포크의 파라미터가 그대로 남는다. 조기 종료는 검증 손실의 최솟값이 `patience` 에포크 동안 갱신되지 않을 때 일어나므로, 남는 파라미터는 최적 에포크보다 `patience` 에포크만큼 더 학습한 상태다. 본문 예제에서 최적 에포크 시점의 파라미터를 따로 복사해 둔 이유가 여기서 다시 드러난다.

자주 쓰는 콜백이 몇 가지 더 있다.

- `ModelCheckpoint` - 에포크마다 모델을 파일로 저장한다.
- `ReduceLROnPlateau` - 검증 손실이 나아지지 않으면 학습률을 줄인다.
- `CSVLogger` - 에포크별 손실과 지표를 CSV로 남긴다.

## 5. 데이터 증강 - 변환이 아니라 계층으로

본문 [코드 5-15]는 조금 번거로운 코드였다. `transforms.RandomHorizontalFlip()`은 **데이터셋에 붙는 변환**이라서 지금이 훈련 중인지 검증 중인지 알지 못한다.
그래서 증강을 적용한 데이터셋과 적용하지 않은 데이터셋을 각각 만들고, **같은 시드로** 분리해 훈련 쪽 40,000개와 검증 쪽 10,000개가 겹치지 않도록 맞춰야 했다.

케라스의 `layers.RandomFlip`은 **모델 안에 들어가는 계층**이다.

```python
model = keras.Sequential([
    layers.Input(shape=(3, 32, 32)),
    layers.RandomFlip('horizontal'),    # 학습할 때만 동작
    ...
])
```

드롭아웃과 마찬가지로 학습할 때만 동작하고, 평가할 때는 입력을 그대로 흘려보낸다. 덕분에 훈련과 검증이 같은 데이터셋을 공유해도 문제가 없으므로 **데이터셋을 두 벌 만들 일이 없다.** [코드 5-14]와 [코드 5-15] 둘 다 케라스 API에서는 필요가 없는 셈이다. 본문 예제의 증강 변환은 모드와 상관없이 데이터셋에 적용되었다는 점(201쪽)에서 다르다.

하지만 케라스의 방식이 더 낫다는 뜻은 아니다. 두 방식은 증강을 **어디에서** 하느냐가 다르다. `transforms` 쪽은 데이터로더가 CPU에서 증강하고, 케라스의 전처리 계층은 모델의 일부이므로 **GPU에서** 증강한다. 어느 쪽이 유리한지는 증강의 무게와 데이터 적재가 병목인지에 따라 달라진다.

덧붙여, 증강 계층이 모델 안에 있으면 저장할 때 함께 저장된다. 같은 방식으로 `Rescaling`, `Normalization` 같은 전처리 계층도 모델에 포함해 배포할 수 있다.

## 6. 가속기와 학습 모드 - 신경 쓰지 않는다

본문 [코드 5-17]부터 [코드 5-19]까지는 하드웨어 가속기를 다뤘다.
장치 객체를 만들고, 모델과 입력 텐서를 `.to(device)`로 옮기고,
서드파티 라이브러리에 넘기기 전에 다시 CPU로 되돌렸다.

케라스에서는 이 부분의 구현이 모두 사라진다. 사용 가능한 가속기를 찾아 모델과 데이터를 옮기는 일을 케라스가 알아서 한다. 예제 노트북에서 모델 세 개를 학습시키는 동안 `.to(device)`가 한 번도 나오지 않는다는 점을 확인해 보자.

`model.train()`과 `model.eval()`도 없다. `fit()`은 학습 모드로, `evaluate()`와 `predict()`는 평가 모드로 자동 전환한다. 5-3절에서 설명한 대로 드롭아웃은 학습 모드에서만 동작해야 한다. `eval()` 호출을 빠뜨려 평가할 때도 드롭아웃이 적용되는 실수를 케라스에서는 원천적으로 예방할 수 있다.

**편해진 만큼 감춰진 것도 있다.** 모드가 언제 바뀌는지, 텐서가 언제 어디로 옮겨지는지가 코드에 드러나지 않는다. 뜻대로 동작하지 않을 때 들여다볼 곳이 줄어든다는 뜻이기도 하다.

## 7. 학습 속도는?

케라스는 배치마다 파이썬 수준의 일을 조금 더 한다. 학습 단계를 감싸고, 지표를 모으고, 콜백을 호출한다. 그만큼 순수 파이토치보다 느리다.

같은 장비(RTX 4070 SUPER)에서 이 글의 CIFAR-10 분류기를 같은 설정으로 학습시켜 재 보면, **파이토치 111초, 케라스 148초로 1.3배가량** 차이가 난다. 모델이 훨씬 가벼우면 이 비율은 커지고(연산 대비 오버헤드의 몫이 커지므로), 모델이 무거우면 1에 가까워진다.

정리하면 이렇다.

- 배치 크기가 작고 모델이 가벼운 실험에서는 오버헤드가 눈에 띈다.
- 실무 규모의 모델에서는 대체로 무시할 만하다.
- GPU 지원 자체에는 아무 문제가 없다. 파이토치가 쓰던 CUDA를 그대로 쓴다.

다만 이것이 전부는 아니다. 여기 1.3배는 **배치마다 붙는 고정 비용**이라 예측 가능한 값이지만, 계층에 따라서는 훨씬 크게 벌어지기도 한다. 이어지는 [keras-api-2](../keras-api-2/) 7절에서 같은 장비에서 10배 가까이 차이 나는 경우를 다룬다. 고수준 API에는 **잘 닦인 길과 그렇지 않은 길**이 있고, 어느 쪽인지는 직접 재 봐야 알 수 있다.

---

## 8. 케라스 API의 한계

케라스로 이 책 전체 예제를 대체할 수는 없다. 몇 가지 예를 들면,

- **트랜스포머**(10장). 케라스 본체에는 `MultiHeadAttention`과 `LayerNormalization`은 있지만 `nn.TransformerEncoderLayer`에 해당하는 것이 없다. 별도 패키지인 KerasHub를 써야 한다.
- **훅**(8-2절, 심화 학습 자료 '파이토치 훅'). 파이토치의 `register_forward_hook()`에 해당하는 케라스 자체 API 기능이 없다.
- **`pack_padded_sequence`**(9장). 가변 길이 시퀀스를 다루는 방식이 다르다.
- **파라미터 그룹별 학습률**(7장), **양자화와 LoRA**(12장). 본격적으로 활용하려면 파이토치 생태계 쪽 도구가 별도로 필요하다.

케라스는 많이 쓰는 구조의 모델을 짧은 코드로 구현하는 데 강하고, 이외의 모델을 만들 때는 파이토치가 강하다.

이어지는 [keras-api-2](../keras-api-2/)에서는 6-3절의 순환 신경망을 케라스로 옮기면서, 두 프레임워크가 **같은 수식을 다르게 구현하는** 지점을 확인해 본다.

## 연습 문제

**1.** `build_classifier()`가 만든 케라스 모델과 `CIFAR10ConvClassifier()`가 만든 파이토치 모델의 계층별 파라미터 수를 각각 출력해 나란히 비교해 보자.

> 힌트: 파이토치 모델은 `named_children()`으로 하위 모듈을 순회할 수 있다.

**2.** 3절의 `padding='same'`을 `padding='valid'`로 바꾸면 `Flatten()` 뒤의 텐서 크기가 어떻게 달라지는지 `summary()`로 확인해 보자. 그리고 본문이 왜 `padding`을 2와 1로 지정했는지 설명해 보자.

**3.** 4절의 `compile()`에서 `from_logits=True`를 빼면 어떤 일이 벌어질까? 먼저 예상해 본 다음 실제로 학습시켜 정확도를 확인하고, 왜 그런 결과가 나오는지 설명해 보자.

**4.** `EarlyStopping`에서 `restore_best_weights=False`(기본값)로 두고 학습시킨 뒤 평가 정확도를 측정해 보자. `True`일 때와 얼마나 차이가 나는지 확인하고, 본문의 `best_model_params` 변수가 왜 필요했는지 설명해 보자.

**5.** 5절의 `layers.RandomFlip('horizontal')`을 `'horizontal_and_vertical'`로 바꿔 학습해 보자. 평가 정확도가 어떻게 달라지는지 확인하고, CIFAR-10 이미지의 성격과 연결해 그 이유를 설명해 보자.

**6.** [도전 문제] `keras.callbacks.ReduceLROnPlateau`를 추가해 검증 손실이 나아지지 않을 때 학습률을 줄이도록 하고, 학습 곡선이 어떻게 달라지는지 관찰해 보자.

**7.** [도전 문제] 이 노트북은 `keras.Sequential`로 모델을 만들었다. `keras.Model`을 상속한 클래스로 같은 모델을 다시 만들어 보고, 본문의 `nn.Module` 상속 방식과 무엇이 같고 무엇이 다른지 정리해 보자.

> 힌트: `__init__()`에서 계층을 만들고 `call()`에서 이어 붙인다. 파이토치의 `forward()`에 해당하는 것이 `call()`이다.

연습 문제의 풀이는 따로 싣지 않았다. 모두 예제 노트북의 코드를 조금씩 고쳐 직접 돌려 보는 문제이고, **결과를 예상한 다음 확인하는 것**이 이 문제들의 요점이기 때문이다. 다시 학습시켜야 하는 문제는 시간이 걸리므로 에포크 수를 줄여 경향만 확인해도 된다.
